  `quarkusAppPartsBuild` task.

## CI-28707659401-02: Gradle composite dev mode does not see source changes

Jobs:

- `Gradle Tests - JDK 25`

Failed tests:

- `io.quarkus.gradle.devmode.BasicCompositeBuildExtensionProjectDevModeTest.main`

Evidence:

- `extracted/build-reports-1-Gradle Tests - JDK 25/integration-tests/gradle/target/surefire-reports/TEST-io.quarkus.gradle.devmode.BasicCompositeBuildExtensionProjectDevModeTest.xml`

Failure signature:

- Expected response to contain `hello from modifiedB and LibA extension enabled: true`
- Actual response remained `hello from LibB and LibA extension enabled: true`

Initial assessment:

- Branch-caused until proven otherwise. This is the same observable symptom as
  stale dev-mode project dependency source tracking.

Fix:

- The task-built serialized application model only described projects from the
  current root build. Dev mode could start with included-build jars but did not
  have workspace module source information for included builds, so changes in
  included projects were not part of the reloadable source graph.
- `ProjectDescriptorBuilder.buildForApp()` now includes projects from the
  current build's included builds without walking parent Gradle builds. It also
  initializes source directories after each module has been evaluated, using the
  actual source sets when present.
- The extension deployment dependency pass now removes a dependency from the
  reloadable local-project set when the same dependency is later reached through
  a non-reloadable extension deployment path. Manual inspection of the generated
  model for `basic-composite-build-extension-project` showed
  `local-projects = [org.acme.libs:libraryB::jar, io.quarkus.test.application:application::jar]`
  and `libraryA` flags without `RELOADABLE`.

Proof:

- `./gradlew -p gradle-model clean build -S --stacktrace --configuration-cache --no-daemon`
  from `devtools/gradle`
- `./mvnw -f devtools/gradle/pom.xml install -DskipTests`
- `./mvnw -f integration-tests/gradle/pom.xml -Dtest=io.quarkus.gradle.devmode.BasicCompositeBuildExtensionProjectDevModeTest,io.quarkus.gradle.devmode.BasicCompositeBuildProjectDevModeTest,io.quarkus.gradle.devmode.IncludedKotlinBuildDevModeTest,io.quarkus.gradle.devmode.JandexIncludedBuildTest test`

## CI-28707659401-06: JVM Gradle model Windows failure

Build-report failures:

- `Quarkus - Gradle Model`
- Maven goal: `org.codehaus.mojo:exec-maven-plugin:3.6.3:exec (gradle)`
- Message: `Command execution failed`

Evidence:

- `extracted/build-reports-1-JVM Tests - JDK 17 Windows/target/build-report.json`
- `raw-logs/4_JVM Tests - JDK 17 Windows.txt`

Failure signature:

- `GradlePomResolverTest > shouldPrefetchGavPomFromGradleRepository() FAILED`
  at `GradlePomResolverTest.java:169`
- Four `DependencyDataCollectorTest` failures caused by
  `org.junit.jupiter.api.io.TempDirDeletionStrategy$DeletionException`

Initial assessment:

- Branch-caused test bug. The POM resolver assertion expected `/` path
  separators. The dependency collector tests resolve from a synthetic Maven
  repository inside a JUnit temp directory; Gradle can keep those files locked
  long enough on Windows that JUnit temp cleanup fails after the assertion
  succeeds.

Fix:

- Normalize the path separator in the POM resolver assertion.
- Disable JUnit cleanup for the dependency collector test temp directory and
  document the Windows file-lock reason.

Proof:

- `./gradlew -p gradle-model clean test --tests io.quarkus.gradle.tooling.GradlePomResolverTest --tests io.quarkus.gradle.tooling.dependency.DependencyDataCollectorTest --stacktrace --no-daemon`
  from `devtools/gradle`
- `./gradlew -p gradle-model clean build -S --stacktrace --configuration-cache --no-daemon`
  from `devtools/gradle`
