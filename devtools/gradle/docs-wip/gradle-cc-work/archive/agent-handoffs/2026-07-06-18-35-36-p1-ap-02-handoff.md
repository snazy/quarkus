## Decisions And Assumptions

Decisions:

- New explicit task names should not sync to legacy output directories by
  default.
- The old task hierarchy can keep `ForcedPropertieBuildService` and current
  dynamic behavior.
- Users migrating to new tasks get the Gradle-friendly model; users staying on
  old tasks get current semantics plus warnings.
- `quarkusBuild` remains the compatibility command and legacy materialization
  path.
- Old Java task types can be deprecated for removal later once new replacements
  exist.
- `QuarkusPlugin` should have separate old/new registration code paths.
- A small scoped registration context object is acceptable if it reduces
  parameter threading and makes later legacy removal easy.
- Do not make this a broad `QuarkusPlugin` refactor.

Assumptions:

- Quarkus 4.0 can introduce new tasks and warnings.
- Quarkus 4.1 can deprecate old Java task types for removal where replacements
  exist.
- `QuarkusBootstrap.Builder.setTargetDirectory(Path)` can be used by new tasks
  to target isolated output roots; compatibility, not core capability, is the
  main blocker.
- New task hierarchy can be built incrementally without changing old task
  behavior first.

Confidence:

- High that the hidden-state problem is isolated to old dynamic paths.
- High that `gen/` and `app/` are shape-specific.
- High that `dep/` can be reused only where dependency layout/filtering
  semantics match.
- Medium on the exact output-manifest opportunities in Quarkus core; current
  APIs are not enough for a complete manifest.
